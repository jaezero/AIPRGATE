# AiPrGate 관리 앱 요구사항

2026-10-25 사용자의 정정: 만들 제품은 **PR 목록·검사 결과·사람 승인을
한 화면 흐름에서 관리하는 앱**이다. GitHub 자동화만으로 제품 완성을 대신하지 않는다.
이 문서는 요구사항과 설계 기준이며 실제 구현·검증 범위는 8절과 진행 기록에서 구분한다.

## 1. 제품과 역할

기존 Android/Kotlin/Compose 프로젝트를 PR 관리 앱으로 전환하는 것을 제안한다.
현재 할 일 앱은 검사 대상 샘플로 보존한다. 분리 위치와 모듈 변경은 구현 단계에서 정한다.
요구사항 정리 이후 사용자의 "진행해" 요청으로 관리 앱 구현을 진행했다.
샘플의 원래 코드는 유지하고 별도 SampleActivity로 진입하도록 했다.

- 작성자: 자신의 PR 정보·AI 사용 근거·자동 검사·리뷰 요청을 확인한다.
- 리뷰어: 변경 코드와 근거를 읽고 의견·수정 요청·승인을 제출한다.
- 저장소 관리자: GitHub 권한·필수 체크·리뷰·브랜치 보호를 관리한다.
- 앱은 로그인한 사용자의 권한으로 동작하며 관리자를 가장하거나 권한을 자체 부여하지 않는다.

## 2. 최소 구현 범위

| 화면 | 필수 기능 |
|---|---|
| 연결 | GitHub 사용자 인증, 로그아웃, 대상 저장소 선택, 접근 실패 안내 |
| PR 목록 | 번호·제목·작성자·업데이트 시각·열림/닫힘/병합 상태, 검사·승인 요약, 새로고침 |
| PR 상세 | 목적·본문·AI 사용 기록·테스트 근거·최신 커밋, 변경 파일과 diff 조회 |
| 검사 결과 탭 | 네 검사별 대기/실행/통과/실패/취소/오류, quality-gate, 경고·차단 원인과 근거 |
| 리뷰·승인 탭 | 리뷰 이력, 의견 작성, 수정 요청, 승인, 대상 커밋과 승인 유효성 표시 |
| 병합 영역 | 병합 가능/불가/확인 중과 사유, 권한·검사·리뷰 최신 상태 재조회, 확인 후 병합 요청 |

PR 상세 안에서 요약·변경 코드·검사·리뷰 탭을 이동하도록 제안한다.
모든 로그와 diff를 한 화면에 한꺼번에 펼치는 의미의 “한 화면”은 아니다.
PR을 나가지 않고 필요한 근거와 승인 동작에 접근하는 것이 목표다.
전체 로그나 지원하지 않는 diff는 GitHub 원문으로 연결하고 그 범위를 명시한다.

## 3. 동작 흐름

```text
개발자: Android Studio 등에서 코드 수정·테스트 → GitHub push·PR 생성
GitHub Actions: PR 정보 / 빌드·JUnit / Lint / Gitleaks 검사 → quality-gate
관리 앱: 로그인 → 저장소 선택 → PR 목록 → PR 상세
         → 최신 커밋의 검사·변경 코드·AI 사용 근거 확인
         → 실패: 사유 확인 → 개발자가 수정·push → 재검사 결과 갱신
         → 통과: 리뷰어 의견·수정 요청·승인 → GitHub 반영 결과 확인
         → 검사·리뷰·보호 조건 충족 → 사용자 확인 → 병합 요청·결과 확인
```

PR 생성과 코드 편집은 우선 개발 도구/GitHub에서 한다.
모바일에서 코드를 작성하거나 자체 빌드 서버를 만드는 것은 최소 범위에 넣지 않는다.
승인·병합은 자동으로 실행하지 않고 사용자가 명시적으로 제출한다.

## 4. 상태와 정합성

- PR의 열림/닫힘/병합 상태, 자동 검사 상태, 사람 리뷰 상태는 별도 값이다.
- 검사 PASS를 승인 완료나 병합 가능으로 바꾸지 않는다.
- 앱에 표시한 결과가 어느 head SHA/run/attempt의 것인지 식별한다.
- 새 커밋이 있으면 예전 검사·승인을 최신 것으로 재사용하지 않는다.
- 승인 제출 전 최신 head를 재조회하고 바뀌었다면 다시 검토하도록 한다.
- 병합 요청은 확인한 head SHA를 대상으로 하며 GitHub의 실제 응답으로 성공 여부를 결정한다.
- 오프라인·권한 부족·API 조회 오류·병합 가능 여부 계산 중을 통과로 표시하지 않는다.
- 승인 버튼을 누른 것만으로 로컬 승인 상태를 확정하지 않고 서버 결과를 확인한다.
- 최초 버전은 화면 진입·복귀·사용자 새로고침으로 갱신한다.
  백그라운드 푸시 알림과 실시간 동기화는 후속 범위다.

## 5. 구성과 기존 코드 재사용

```text
Android 관리 앱
  ↕ 사용자 인증을 거친 GitHub API
GitHub: 저장소·PR·변경 파일·Actions/checks·리뷰·병합·브랜치 보호
  ↕
기존 네 검사와 quality-gate
```

기존 `.github/`, `policy/`, `tools/pr-gate/`를 검사 기반으로 재사용한다.
앱이 빌드·Lint·시크릿 검사를 기기 안에서 다시 실행하지 않는다.
관리 대상 저장소에는 검사 워크플로우와 정책이 있어야 한다.
파일럿 기준은 현재 Android 샘플에 한정되며 모든 언어의 저장소를 지원한다고 하지 않는다.

GitHub App의 사용자 device flow와 개인 access token 연결을 구현한다.
배포용 Client ID는 제공받지 않아 앱의 연결 설정에서 공개 ID를 입력한다.
개인 토큰은 본인의 토큰을 앱 안에서 직접 입력하고 사용자를 검증한 후 보관한다.
공유 봇 계정으로 사람 승인을 대신하지 않는다.
앱 비밀키·client secret을 APK에 포함하지 않는다.
현재 두 인증 경로와 GitHub API 조회·리뷰·병합에는 별도 백엔드를 추가하지 않는다.
로그인 토큰을 소스·문서·로그·평문 Room에 보관하지 않는다.

공식 확인 자료:
- GitHub 문서의 GitHub App 사용자 access token/device flow 설명.
- GitHub REST의 pull requests 및 pull request reviews API.

## 6. GitHub 저장소 준비

화면·상태 모델·테스트용 가상 데이터는 저장소 없이 개발할 수 있다.
다만 실제 인증·PR 조회·Actions 결과·승인·병합 인수에는 실제 저장소가 필요하다.
가상 데이터 모드는 표시를 분리하고 실제 연동 완료로 계산하지 않는다.

권장 준비:
1. 테스트용 저장소 1개: 처음에는 관리 앱 코드와 검사 대상 샘플을 같은 저장소에 둘 수 있다.
2. 저장소 owner/name 또는 주소: 기존 저장소가 있다면 새로 만들 필요는 없다.
3. Actions 실행과 보호 설정을 확인할 수 있는 관리자.
4. 작성자와 리뷰어 두 사람의 계정: 실제 작성자 외 승인 시나리오용.
5. 앱 등록·사용자 인증 설정: 실제 연동 단계에서 관리자와 함께 준비한다.

테스트용 저장소이므로 실제 운영 코드를 대상으로 승인·병합을 시험하지 않는다.
토큰·비밀번호를 채팅으로 전달하도록 요청하지 않는다.
저장소 생성·게시·보호 변경·리뷰 제출·병합 같은 외부 쓰기는
대상과 동작에 대한 사용자의 명시적 허가 없이 실행하지 않는다.

### 제공받은 대상

사용자가 제공한 Git 원격 주소: `https://github.com/jaezero/AIPRGATE.git`.
2026-10-25 공개 페이지에서 main과 기존 파일을 읽기 전용으로 확인했다.
새 저장소를 만들 필요는 없다. 원격의 기존 코드와 로컬 변경의 관계를 먼저 확인한 뒤
연결 방식을 정한다. 주소 제공만으로 커밋·푸시·리뷰 제출·보호 변경을 실행하지 않는다.
관리자 권한·사용자 인증 등록·두 사람의 실제 승인 시나리오는 아직 확인하지 않았다.

## 7. 구현 순서와 완료 기준

1. 관리 앱 화면·상태·탐색 구조와 샘플 앱 보존 방식을 구현한다.
2. 실제 사용자 인증·저장소 선택·PR 목록·본문·diff를 연결한다.
3. 최신 커밋의 검사·quality-gate 결과와 근거를 연결한다.
4. 실제 리뷰·수정 요청·승인·병합과 오류 처리를 연결한다.
5. 두 사용자로 실패 → 수정 → 재검사 → 리뷰 → 승인 → 병합을 인수 검증한다.

완료는 실제 PR을 앱에서 조회하고, 검사 실패 원인을 확인하고,
코드 수정 후 최신 결과를 확인하고, 다른 사용자가 앱에서 리뷰·승인하여
GitHub에 반영되고, 보호 조건을 지키며 병합 결과를 확인한 상태다.
화면만 있는 시제품, 자동 검사만 있는 저장소, 가짜 승인 상태는 완료가 아니다.

## 8. 현재 상태

관리 앱의 목록·상세·본문·diff·검사·리뷰·확인창·병합 조건과 실제 API 호출 코드를 구현했다.
GitHub 사용자 확인 후 암호화 토큰 보관, device flow·개인 토큰, 로그아웃을 구현했다.
기존 할 일 앱은 별도 진입점과 기존 DB를 보존한다.
실제 인증·리뷰 제출·승인·병합 인수는 구현 여부와 별개로 계정 준비와 사용자 동작이 필요하다.
최신 실측과 미확인 항목은 [개발 진행 기록](development-progress.md)을 따른다.
