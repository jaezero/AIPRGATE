# 리뷰 코멘트 생성 파인튜닝 — 도입 검토 및 변경 제안

작성일: 2026-09-21. 상태: 계획만 작성. 모델 다운로드·추론·학습·데이터 생성·수집은 수행하지 않았다.

사용자 확인: 파인튜닝 목표는 **리뷰 코멘트 생성 — 문제 근거와 검토 의견 작성**이다. 위험 분류기 개발이나 수정 코드 자동 생성으로 확대하지 않는다.

## 1. 현재 판단

**현재 MVP에 모델 파인튜닝이 반드시 필요하다는 근거는 없다.** 기준 앱과 검사 룰·리뷰 데이터·비교 평가가 아직 없으므로, 파인튜닝의 효과를 증명할 기준선도 없다. 자동 게이트를 우선 완성하고, 학습 없는 방식으로 남는 문제가 관찰될 경우에만 별도 실험으로 진행한다.

연구 질문: 동일한 변경 코드·정책·검사 결과를 제공했을 때, 소형 모델의 리뷰 코멘트 파인튜닝이 학습 전 모델의 개선된 프롬프트보다 **사실에 근거하고 개발자가 활용할 수 있는 한국어 의견**을 더 잘 작성하는가?

처음에는 이미 확인된 finding을 설명하는 범위로 제한한다. 모델이 새로운 취약점을 잘 찾아낸다는 주장은 별도 평가가 필요하다. 자동 분석 도구 자체가 잘못 탐지한 내용을 더 유창하게 설명해도 개선으로 인정하지 않는다.

## 2. 학습 없이 가능한 것과 학습 검토 대상

| 문제 | 우선 해결 방식 | 파인튜닝 필요성 판단 |
|---|---|---|
| 컴파일·테스트 실패 탐지 | Gradle·테스트 | 학습 불필요 |
| 검증된 시크릿·품질 패턴 탐지 | 선정 룰 | 학습으로 대체하지 않음 |
| 누락·취소·SHA 불일치·병합 승인 | 결정적 집계·보호 규칙 | 학습 불필요 |
| 룰 설명과 위치를 일정한 양식으로 제시 | 사람이 작성한 룰별 템플릿 | 우선 비교 기준선 |
| 정책·Android 맥락에 맞춘 설명 | 같은 모델에 정책 발췌·주변 코드·구조화 프롬프트 제공 | 반복되는 잔여 오류를 측정한 뒤 판단 |
| 근거 인용·간결한 한국어·확인 방법의 일관성 | 프롬프트·예시 개선, 이후 SFT 후보 | 검증된 학습 쌍과 개선 여지가 있을 때 검토 |
| 필요한 문맥이 누락된 경우 | 문맥 보강 또는 판단 보류 | 학습으로 부족한 사실을 만들어내지 않음 |
| 정확한 자동 수정·새 취약점 발견 | 별도 과제 | 이번 목표 밖 |

SFT는 원하는 입력→출력 형태를 학습하는 후보 방법이다. 최신 Android 사실·보안 지식의 정확성을 자동 보장하지 않는다. [TRL SFT 안내](https://huggingface.co/docs/trl/main/en/sft_trainer)

## 3. 입력·출력·배치 위치

입력: PR diff, 필요한 주변 코드, 관련 요구사항·정책 발췌, 도구의 원본 finding과 실행 상태. 모델 입력에 사람의 정답 코멘트나 수정 후 정답 코드를 포함하지 않는다. 실행 오류를 코드 위반 finding으로 바꿔 넣지 않는다.

출력 계약: `file/line`, `finding 또는 정책 근거`, `문제 이유·영향`, `검토 또는 수정 방향`, `확인할 테스트`, `불확실성·추가 문맥 필요`. 문제가 확인되지 않았으면 불필요한 지적을 만들지 않는 응답도 허용한다. 입력 밖 룰 ID·파일·API·근거를 생성하면 오류로 평가한다.

위치는 개발 PC 또는 별도 평가 환경이다. Android 앱에 모델을 넣지 않고, 초기에는 오프라인 보고서로만 확인한다. GitHub PR 자동 코멘트 게시·API 운영·병합 차단 연결은 별도 후속 도입이다. LLM 결과는 승인 권한이나 `quality-gate` 성공 조건을 바꾸지 않는다.

코드 주석·PR 본문의 모델 지시는 신뢰하지 않는 데이터로 취급한다. 시크릿을 마스킹하고 필요한 문맥만 전달한다. 외부 서비스 전송은 데이터 권한·비용 조건을 다시 확인해야 한다.

## 4. 대상 모델과 실행 환경 후보

| 선택 | 후보·이유 | 남은 확인 |
|---|---|---|
| 첫 기준선·SFT 후보 | `Qwen/Qwen2.5-Coder-1.5B-Instruct` | 소형 코드 모델로 로컬 실험 후보. Kotlin·한국어 리뷰 품질은 미검증 |
| 확장 비교 후보 | `Qwen/Qwen2.5-Coder-7B-Instruct` | 추가 GPU 자원이 확보되고 소형 모델의 한계가 확인될 경우. 초기 필수 아님 |
| 학습 방식 | PEFT LoRA, 필요 시 양자화 기반 방식 검토 | 실제 CUDA·PyTorch·Transformers·PEFT·TRL·양자화 라이브러리 호환성 파일럿 필요 |

두 모델의 공식 카드에 Apache-2.0이 표시되어 있다. 실제 사용할 모델·tokenizer revision을 해시로 고정하고 해당 revision의 라이선스·배포 조건을 보존한다. ‘최신·최고 모델’이라는 이유로 선정한 것이 아니다. [1.5B 모델 카드](https://huggingface.co/Qwen/Qwen2.5-Coder-1.5B-Instruct), [7B 모델 카드](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct)

LoRA는 전체 가중치 대신 추가 저랭크 파라미터를 학습하는 방식이다. 메모리 부담을 줄이는 후보지만 이 GPU에서 원하는 입력 길이로 학습 가능하다는 보장은 아니다. [PEFT LoRA 문서](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora)

실측 하드웨어는 RTX 3050 8GB, 드라이버 560.94다. 이번에는 CUDA 런타임·학습 라이브러리·WSL 환경 호환성을 확인하지 않았다. 학습 환경은 Android Gradle과 분리한 Linux/WSL2 환경을 우선 후보로 검토한다. 드라이버 업데이트나 환경 설치를 자동 진행하지 않는다.

파일럿에서 짧은 입력·작은 배치로 추론/학습 최대 VRAM·처리 속도를 측정하고, 실제 diff 길이 분포에 따라 입력 한도를 정한다. 컨텍스트가 잘리면 조용히 정상 리뷰로 처리하지 않고 잘림을 기록한다. 메모리 부족 시 길이·배치·adapter 범위 조정 후 다시 평가하며, 큰 모델로 바꾸는 것을 자동 해결책으로 삼지 않는다.

## 5. 데이터 출처와 사용 권한

| 출처 | 사용 조건 |
|---|---|
| 팀 자체 코드·실제 리뷰 | 작성·공유·학습 권한과 팀원의 동의 범위, 원본 SHA·작성자 기록 |
| 오픈소스 Kotlin/Android 변경·리뷰 | 파일·저장소 라이선스뿐 아니라 리뷰 코멘트의 사용 조건·출처 확인. 공개되어 있다는 이유만으로 자동 수집 금지 |
| 의도적으로 만든 검증 사례 | 추후 별도 데이터 제작 단계에서만 작성. 주입 사실·원형 코드·정답 근거 표시 |
| 외부 모델 출력 | 서비스 약관·학습 사용 권한 확인, 사람 검토 필요. 모델 출력 자체를 정답으로 삼지 않음 |

최초에는 권한을 명확히 할 수 있는 팀 자료를 우선한다. 샘플 앱 하나의 반복 변형만 확보되면 일반화 성능을 주장할 수 없다. 그 경우 다른 프로젝트 평가를 확보하거나 ‘해당 앱에 대한 예비 실험’으로 결론을 제한한다.

권한 불명확 자료·실키·개인정보·제3자 비공개 코드는 제외한다. 학습·검증·테스트 각각 provenance 명세와 제외 사유를 남긴다. 이 문서 작성 과정에서는 학습 데이터 파일이나 코드-리뷰 쌍을 만들지 않았다.

## 6. 라벨 기준과 정답 작성

각 기록에 `sample_id, project_id, PR/commit, origin_family_id, 원형·변형 관계, 출처·권한, 코드/정책/도구 revision, diff·문맥, finding, 검토된 코멘트, 근거, 판정자, 이견, split`을 둔다.

- 사실 오류: 코드에 없는 동작·파일·API·룰을 주장하면 부정확.
- 위치: 해당 변경 또는 직접 관련 맥락을 정확히 지목해야 함.
- 근거: 정책·실제 검사 결과와 일치하고 실행 오류와 코드 결함을 구분해야 함.
- 활용성: 왜 문제인지와 어떤 검토·테스트가 필요한지 설명해야 함.
- 불확실성: 부족한 문맥은 확인 요청으로 표현하고 위험을 단정하지 않아야 함.
- 정상·비적용: 문제 없는 변경이나 적용되지 않는 룰에 지적하지 않는 예를 포함.

사람 2인이 독립 검토하고 불일치는 조정한다. 한 명의 평가만 가능하면 그 한계를 공개하고 확정 정답으로 과장하지 않는다. tool finding은 입력 근거 중 하나이며 오탐 검토 없이 정답 라벨로 복사하지 않는다. 단순 문체 다듬기와 내용 정확성 개선을 구분한다.

## 7. 중복 제거와 데이터 분리

행 무작위 분할을 하지 않는다. 원본 코드·관련 PR·수정 전후 쌍·동일 생성 대화·변수명만 바꾼 변형·fork·복제 코드를 하나의 **원형 그룹**으로 묶는다.

절차:

1. 원문 hash 및 공백 정규화 hash로 완전 중복을 찾는다.
2. 토큰/구문 유사도로 이름·주석·형식 변경과 코드 복제를 검토한다. 문자열·API 차이가 의미를 바꾸는 경우 자동 삭제하지 않는다.
3. 동일 원형 그룹은 하나의 split에만 배정한다. 같은 PR의 여러 hunk도 나누지 않는다.
4. 가능하면 프로젝트 단위로 최종 테스트를 분리하고 최신 자체 작성 사례를 포함한다.
5. 그룹 수·위험 영역·정상 비율을 확인한 뒤 학습/검증/테스트 비율과 seed를 정해 고정한다. 적은 그룹에 8:1:1을 기계적으로 적용하지 않는다.
6. 프롬프트 예시·검색 문서·튜닝 입력에도 테스트 정답·코드 변형이 들어가지 않도록 감사한다.
7. 검증 집합으로 prompt·checkpoint·출력 길이를 선택하고 최종 테스트는 선택에 사용하지 않는다. 테스트를 보고 수정했다면 새 독립 테스트를 마련한다.

정책 설명처럼 실제 운영에도 제공되는 공통 지침은 모든 조건에 동일하게 제공할 수 있다. 특정 평가 사례의 정답 리뷰는 지침에 섞지 않는다. 사전학습 데이터 중복은 완전히 확인하기 어려우므로 모델 카드·자료 시점과 잔여 오염 가능성을 보고한다.

## 8. 공정한 비교와 평가 지표

| 조건 | 방식 | 비교 의미 |
|---|---|---|
| B0 | 검증 도구 결과 + 룰별 정적 템플릿 | 모델 없는 운영 기준선 |
| B1 | 고정된 1.5B 모델 + 기본 구조화 프롬프트 | 학습 전 시작점 |
| B2 | 같은 모델 + 검증 집합으로 개선한 프롬프트·예시·정책 맥락 | 학습 없이 달성 가능한 강한 기준선 |
| F1 | 같은 원본 모델 + SFT adapter, B2와 동일한 평가 입력·프롬프트 | 학습 추가 효과 |

입력 finding·코드·문맥, tokenizer, 출력 예산, 생성 설정, 추론 양자화 조건을 맞춘다. 변경한 항목은 별도 변수로 보고한다. B0는 전체 시스템 비교이고, 파인튜닝 효과의 주 비교는 **F1 대 B2**다. 여러 모델을 동시에 바꾸고 학습 효과라고 주장하지 않는다.

평가 단위는 원형 그룹에 속한 코드 변경과 그 리뷰다. 평가자는 방법명을 가린 상태에서 순서를 섞어 평가하고, 문장별 사실성과 코멘트 전체 유용성을 분리한다.

| 지표 | 정의 |
|---|---|
| 근거 정확성 | 근거로 지지되는 사실 주장 수 / 전체 사실 주장 수. 주장 없는 보류 응답은 별도 집계 |
| 실질적 사용 가능 비율 | 위치·근거·영향·확인 방법이 맞고 내용상 큰 수정 없이 쓸 수 있는 코멘트 / 전체 평가 사례 |
| 정상 사례 부당 지적률 | 정상 변경에 잘못된 문제를 주장한 사례 / 정상 사례 |
| 누락·과도한 보류 | 설명할 수 있는 확인된 문제를 누락/보류한 사례 / 해당 사례 |
| 위치·근거 참조 정확성 | 올바른 위치/룰/근거 참조 / 전체 참조 |
| 안전성·형식 | 입력 내 지시문 추종, 민감정보 재출력, 구조 불일치 사례 수 |
| 비용·시간 | 같은 하드웨어에서 사례별 추론 시간·VRAM·토큰, 사람이 고치는 시간 |

모든 응답을 ‘모르겠다’로 만드는 모델이 정확성 지표만 높게 받지 않도록 사용 가능 비율·누락률을 함께 본다. BLEU/ROUGE 같은 문장 유사도나 LLM 단독 채점을 주 성공 기준으로 삼지 않는다.

같은 사례의 paired 차이를 계산하고 원형 그룹 단위 불확실성(예: cluster bootstrap)을 보고한다. 한 원형의 변형을 독립 표본처럼 세지 않는다. 표본이 적으면 개별 실패·건수·평가자 불일치를 함께 공개하고 통계적으로 일반화하지 않는다.

Go/No-Go 기준은 최종 테스트를 보기 전에 고정한다. 최소 유용 개선폭은 코멘트 수정 시간을 줄일 실무 가치와 파일럿 변동성으로 정하고, 정상 부당 지적·근거 환각의 허용 회귀 한도도 함께 정한다. 현재 임의로 ‘정확도 90%’나 ‘100개면 충분’을 약속하지 않는다. 차이를 분별할 독립 그룹이 부족하면 ‘효과 미입증’으로 판정한다.

## 9. 비용·시간·중단 조건

현재 확정 비용은 없다. 모델을 실행하거나 유료 리소스를 주문하지 않았다.

| 항목 | 산정 방식·필요 정보 |
|---|---|
| 데이터 검토 | 독립 그룹 수 × 그룹당 작성/2인 검토 시간 + 이견 조정 |
| 로컬 학습 | 파일럿 step 시간 × 전체 step × 실험 횟수 + 평가 시간. 전력·다른 작업 점유도 기록 |
| 저장 공간 | 모델·tokenizer·adapter·체크포인트·로그의 실측 합계 |
| 클라우드 대안 | 확보 GPU의 실제 시간당 단가 × 예상 시간 + 저장·전송 비용. 사용 전 견적·상한 확정 |
| 운영 | PR당 추론 시간·빈도·실패 복구, 외부 API를 쓰면 입력/출력 토큰 비용 |

파일럿 이후 검토 가능 시간·GPU 시간·최대 실험 횟수 상한을 정한다. 상한에 도달해도 개선이 없으면 그 사실을 보고하고 종료한다. 권한 있는 데이터 부족, 메모리/실행 환경 불가, 낮은 평가자 일치, 누출 없는 테스트 부족, B2 대비 개선 없음 중 하나면 학습을 보류하거나 중단한다.

## 10. PRD·요구사항 변경 제안 — 원본에는 아직 미반영

사용자가 선택한 것은 학습 목표다. 학습 실행·유료 자원·데이터 제작을 승인한 것으로 취급하지 않는다. v2.0의 기본 게이트 범위를 유지하고 아래를 선택 연구 트랙으로 제안한다.

| 문서 위치 | 제안 내용 |
|---|---|
| PRD 4 목표 | G-06 후보: 확인된 검사 결과의 리뷰 설명에 대해 B0/B1/B2/F1을 비교하고 학습 추가 가치·한계를 보고 |
| PRD 5.3 제외 범위 | 오프라인 리뷰 코멘트 비교 실험은 조건부 선택. 자동 AI 리뷰 봇·모델 병합 판정은 계속 후속 |
| PRD 9 생성 기록 | 앱 개발 AI 기록(EVD)과 리뷰 모델 학습 데이터 계보를 구분 |
| PRD 10 검증 | 앱·룰·게이트 검증과 별도로 원형 그룹 분리·블라인드 리뷰 평가 추가 |

| SRS NFR-07 | 로컬 실험 후보를 명시하되 유료 API·클라우드 자동 도입 금지 유지 |
| SRS GAT/GOV | 모델의 지연·오류·설명 결과가 필수 게이트와 사람 승인 조건을 변경하지 않음 |

선택 트랙을 채택할 경우 내부 필수 요구사항 후보:

| ID 후보 | 요구사항·인수 증거 |
|---|---|
| FT-01 | 리뷰 설명만 생성하며 자동 수정·차단 없음. 출력 역할 검사 |
| FT-02 | 출처·권한·원형 그룹·라벨 검토 기록 없는 샘플 사용 금지. provenance 감사 |

| FT-04 | 모델/revision·tokenizer·adapter·라이브러리·seed·설정·입력 한도 기록. 학습 manifest |
| FT-05 | B0/B1/B2/F1을 같은 고정 테스트에서 비교. paired 결과·실패·불확실성 보고 |
| FT-06 | 민감정보·입력 지시문·잘림·판단 보류 처리. 정상·문맥 부족 사례 평가 |

AC-FT 후보: 학습 성공 여부만으로 완료하지 않고 누출 감사, 고정 기준선 비교, 비용·한계 보고를 모두 확인한다. 효과 미입증도 정직한 실험 결론이며 MVP 게이트 실패와 구분한다.

## 11. 일정 변경안

아래는 담당·가용 시간 확인 전의 작업량 추정이다. 병렬 인력 투입이나 완료 일정을 보장하지 않는다.

| 순서 | 작업 | 대략적 작업일·종료 조건 |
|---|---|---|
| FT-A | 목표·권한·평가 계약·비용 상한 정리 | 1~2일, 실행 범위와 책임 확정 |
| FT-B | 소규모 검토 자료 확보·B0/B1/B2 평가 | 3~5일, 학습 없이 남는 문제 확인. 자료 수집은 별도 착수 후 |
| FT-C | 독립 그룹 데이터·라벨·분리 감사 | 5~10일 이상 가능, 필요 규모와 검토 인력에 좌우 |
| FT-D | 하드웨어 파일럿·제한된 adapter 학습 | 1~3일 이상 가능, GPU 속도·실패에 따라 재산정 |
| FT-E | 고정 테스트·블라인드 채점·보고 | 2~4일, 개선 또는 미입증 결과 보고 |

직렬 약 12~24 작업일 이상의 별도 부담을 예상한다. 데이터 확보가 느리면 더 길어진다. 기존 종료 예정일 2026-10-30 안에 기본 앱·게이트와 모두 완료한다고 약속하기 어렵다. 우선 FT-A/B에서 필요성을 판단하고, 본학습은 자원·일정이 확인될 때만 채택한다. 부족하면 이번에는 기준선 비교와 학습 계획까지 보고하고 본학습을 후속으로 넘기는 안을 제안한다.

## 12. 결론과 남은 결정

비교 평가 설계는 가능하지만 **현재는 데이터·기준선·독립 테스트가 없어 개선 여부를 판단할 수 없다.** 첫 선택은 앱/게이트 완성과 학습 없는 리뷰 기준선 확보다. 파인튜닝의 채택 여부는 그 결과에서 결정한다.

남은 결정: 한국어 리뷰 출력의 실제 요구 수준, 사용할 자체 자료와 검토자, 독립 프로젝트 자료 확보 가능성, 실험 시간·비용 상한, 실행 환경과 도구 revision. 이 문서는 계획이며 학습 데이터나 학습 성능의 증거가 아니다.
