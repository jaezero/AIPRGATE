| 항목 | 내용 |

## 1. 배경 및 문제 정의

### 1.1 현장 문제
- Copilot, Cursor, Claude 등 AI 코딩 도구로 코드를 빠르게 만드는 "바이브 코딩"이 주류가 되었다.
- 코드 생산 속도는 비약적으로 올라갔지만, 그 코드가 **정확한지·안전한지·유지보수 가능한지** 검증하는 책임은 여전히 개발자에게 있다.
- AI 생성 코드는 "동작은 하지만" 다음 문제를 자주 숨긴다.
  - 하드코딩된 API 키·토큰, 과도한 권한 요청, 안전하지 않은 네트워크 설정
  - 예외 처리 누락, 메인 스레드 I/O 등 성능·안정성 문제
  - 작성자 본인도 이해 못 한 복잡한 구조 → 리뷰 없이 병합 → 운영 장애
- 즉, **AI 시대 개발자의 핵심 역량은 "빨리 짜는 능력"이 아니라 "AI가 짠 코드를 검증하고 통제하는 능력"**이다.

### 1.2 왜 PR 단계인가
- PR(Pull Request)은 코드가 메인 브랜치로 들어가는 **유일한 길목**이다.
- 이 길목에 자동 검증 게이트를 세우면 사람이 놓치는 문제를 기계가 먼저 걸러내고, 사람은 "이해했는가·의도에 맞는가"라는 본질적 리뷰에 집중할 수 있다.

### 1.3 1학기 활동과의 차이
| 구분 | 1학기 (연구형) | 2학기 (구축형, 본 과제) |
|---|---|---|
| 주제 | 연합학습 환경 다기관 의료데이터 성능 영향도 분석 | AI 생성 코드 PR 자동 검증·승인 파이프라인 |
| 산출물 | 실험 결과(CSV, 그래프), 인사이트 | 동작하는 CI/CD 파이프라인 + 샘플 앱 + 운영 문서 |
| 검증 방식 | 지표(AUC/F1) 비교 | 실전 시나리오(취약 코드 PR 차단) 데모 |
| 발표 메시지 | "평균 성능보다 사이트별 해석" | "속도보다 통제, AI 코드는 게이트를 통과해야 병합된다" |

## 2. 목표

### 2.1 프로젝트 목표 (Goal)
"AI가 생성한 안드로이드 코드가 PR로 올라오면 **자동으로 빌드·테스트·정적분석·보안검사**를 거치고, **품질 기준을 통과한 코드만 사람의 승인 후 병합**되는 파이프라인을 실제로 동작하는 형태로 완성한다."

### 2.2 성공 지표 (Success Metrics)
| 지표 | 목표치 | 측정 방법 |
|---|---|---|
| 게이트 차단 정확도 | 의도적으로 주입한 취약 PR 시나리오 10건 중 **10건 차단** | 실전 시나리오 테스트 (11회차) |
| 정상 PR 통과율 | 정상 PR 5건 중 **5건 통과** (오탐 0) | 동일 |
| 파이프라인 실행 시간 | PR 1건당 **10분 이내** | GitHub Actions 로그 |
| 단위 테스트 커버리지 | 핵심 로직(ViewModel/Repository) **60% 이상** | Kover/JaCoCo 리포트 |
| 문서화 | README + 운영 가이드 + 체크리스트 완비 | 결과보고서 10p 이상 |
| 팀원 체득 | 팀원 전원이 PR 생성→검증→승인 플로우를 직접 수행 | 월별 활동보고서 |

### 2.3 비목표 (Non-Goals)
- 상용 수준의 앱 기능 개발 (앱은 **검증 대상**일 뿐, 기능은 최소화)
- iOS, 웹 등 타 플랫폼 지원
- 자체 정적분석 엔진 개발 (검증된 오픈소스 도구를 **조합·설정**하는 것이 목표)
- AI가 리뷰를 완전히 대체하는 것 (AI 리뷰는 **보조**, 최종 승인은 사람)

## 3. 사용자 및 이해관계자

| 역할 | 누구 | 니즈 |
|---|---|---|
| PR 작성자 (개발자) | 팀원 | AI로 만든 코드가 어디가 문제인지 **빠르고 구체적으로** 알고 싶다 |
| 리뷰어 | 팀장/팀원 상호 | 기계가 걸러줄 것은 걸러주고, 나는 **설계·의도**만 보고 싶다 |
| 관리자 (기술 리더) | 산업체 전문가, 지도교수 | 어떤 기준으로 코드가 병합되는지 **정책이 명문화**되어야 한다 |
| 신규 합류자 | 미래의 팀원 | 규칙을 몰라도 **PR 템플릿과 게이트가 알려주는** 환경 |

## 4. 솔루션 개요

### 4.1 한 줄 요약
> GitHub Actions 위에 **6단계 검증 게이트**를 구성하고, 브랜치 보호 규칙으로 "게이트 통과 + 리뷰어 승인" 없이는 main에 병합될 수 없게 만든다.

### 4.2 전체 흐름
```
[개발자] AI 도구로 코드 생성 → feature 브랜치 push → PR 생성 (템플릿 작성)
   │
   ▼
[GitHub Actions 자동 실행]
   ① Build       : Gradle assembleDebug (컴파일 실패 즉시 차단)
   ② Unit Test   : testDebugUnitTest + 커버리지 측정 (기준 미달 차단)
   ③ Static Lint : ktlint(스타일) + Detekt(복잡도·코드스멜) + Android Lint
   ④ Security    : 시크릿 스캔(gitleaks) + SAST(Semgrep) + 의존성 취약점(OWASP/Trivy)
   ⑤ AI Review   : LLM 기반 리뷰 봇 → AI 코드 위험 패턴 코멘트 (보조, 차단 아님)
   ⑥ Quality Gate: ①~④ 결과 집계 → PR에 요약 리포트 코멘트 + 상태 체크 결정
   │
   ▼
[브랜치 보호 규칙] 필수 체크 통과 + 리뷰어 1명 이상 Approve + PR 체크리스트 완료
   │
   ▼
[병합] Squash merge → main
```

### 4.3 핵심 구성요소
| 구성요소 | 역할 | 도구/기술 |
|---|---|---|
| 검증 대상 샘플 앱 | AI 코드가 실제로 들어갈 "그릇" | Kotlin, Jetpack Compose, Room, Retrofit (간단한 메모/할일 앱) |
| 협업 규칙 | 브랜치 전략, 커밋 컨벤션, PR 템플릿 | GitHub Flow, Conventional Commits, PR template, CODEOWNERS |
| CI 파이프라인 | PR 이벤트 시 자동 검증 | GitHub Actions (workflow yaml) |
| 정적 분석 | 스타일·복잡도·안드로이드 특화 이슈 | ktlint, Detekt, Android Lint |
| 보안 검사 | 시크릿·취약 패턴·취약 의존성 | gitleaks, Semgrep(안드로이드 룰셋), OWASP Dependency-Check 또는 Trivy |
| AI 리뷰 봇 | AI 생성 코드 위험 패턴 설명, 리뷰 포인트 제시 | Claude API 기반 GitHub Action (PR diff → 코멘트) |
| 품질 게이트 | 결과 집계, 통과/차단 판정, 리포트 | 커스텀 Action 스크립트 + Branch Protection required checks |
| 문서 | 운영 가이드, 체크리스트, 결과보고서 | Markdown (README, docs/) |

### 4.4 AI 생성 코드 특화 검증 항목 (차별점)
일반 CI와 다른, **"AI가 짠 코드이기 때문에" 집중 검사하는 항목**:
1. **하드코딩 시크릿**: AI가 예제용으로 넣는 `API_KEY = "sk-..."` 패턴 → gitleaks
2. **과도한 권한**: AndroidManifest에 불필요한 `INTERNET`, `READ_EXTERNAL_STORAGE` 등 → Android Lint + 커스텀 Semgrep 룰
3. **안전하지 않은 네트워크**: `usesCleartextTraffic="true"`, 인증서 검증 우회 TrustManager → Semgrep
4. **메인 스레드 블로킹**: 코루틴 없이 네트워크/DB 호출 → Detekt 커스텀 룰 + Lint
5. **예외 삼킴**: `catch (e: Exception) {}` 빈 블록 → Detekt `EmptyCatchBlock`, `TooGenericExceptionCaught`
6. **복잡도 폭증**: 함수 길이·순환 복잡도 초과 → Detekt `LongMethod`, `ComplexMethod`
7. **테스트 없는 변경**: 로직 변경에 테스트 파일 변경이 없으면 경고 → 커스텀 게이트 스크립트
8. **작성자 이해도 확인**: PR 템플릿의 "이 코드가 하는 일을 내 말로 설명" 항목 필수 → 미작성 시 체크 실패

## 5. 범위 및 단계별 계획

현재(9/17) 기준 신청서 회차 일정상 7회차 시점이나 구현 산출물이 없으므로, **남은 기간(약 6주)에 맞춰 3단계로 압축**한다.

### Phase 1 — 기반 구축 (9/18 ~ 9/30, 2주)
- 안드로이드 샘플 앱 최소 기능 완성 (AI 도구 활용, 화면 2~3개)
- GitHub 저장소·브랜치 전략·PR 템플릿·CODEOWNERS 설정
- CI 1차: 빌드 + 단위 테스트 + ktlint/Detekt 자동 실행
- 산출물: 동작하는 앱, `.github/workflows/pr-check.yml`, `CONTRIBUTING.md`

### Phase 2 — 보안·게이트 구축 (10/1 ~ 10/16, 2주)
- 보안 스캔 3종 연동 (gitleaks, Semgrep, 의존성 취약점)
- AI 리뷰 봇 연동 (PR diff 요약 + 위험 패턴 코멘트)
- 품질 게이트 스크립트 + 브랜치 보호 규칙 적용
- 산출물: 6단계 파이프라인 완성, 게이트 정책 문서

### Phase 3 — 검증·고도화·문서화 (10/17 ~ 10/30, 2주)
- 취약 코드 주입 시나리오 10건 + 정상 PR 5건으로 실전 검증
- 산업체 전문가 피드백 반영 (임계값 튜닝, 오탐 조정)
- 결과보고서(10p+), 발표자료, 포스터, 활동수기
- 산출물: 검증 결과표, 최종 보고서, 발표 PPT

## 9. 최종 산출물 목록

2. 파이프라인 아키텍처 다이어그램, 게이트 정책 문서 (`docs/quality-gate-policy.md`)
