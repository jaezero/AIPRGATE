# 자문회의 제안 발표 — 목차 및 PPT 생성 프롬프트

> 용도: 클로우플레이크 방문 자문회의(7회차, 9/18)에서 **"이 주제를 이렇게 만들겠습니다"**를 제안하는 발표.
> 상태: 아직 개발 산출물이 없으므로 결과 발표가 아닌 **기획·설계 제안 발표**로 구성한다.

---

## 1. 1학기 발표와 무엇이 달라야 하는가

1학기 발표(연합학습 의료데이터 연구)의 구조는 `배경 → 데이터 → 실험 설계 → 결과 → 인사이트 → 결론`이었다. 연구형이라 **"무엇을 발견했는가"**가 중심이었다.

이번 주제는 구축형이므로 **"무엇을, 왜, 어떻게 만들 것이며, 완성되면 무엇이 증명되는가"**가 중심이 되어야 한다. 1학기에서 가져올 것과 바꿀 것:

| 1학기에서 유지할 것 | 이번에 바꿀 것 |
|---|---|
| 표지의 3카드 요약 (Data / Experiment / Message) | → (Target / Pipeline / Message) 로 치환 |
| 목차 5개 섹션, 섹션별 한 줄 부제 | 섹션명을 연구 용어 → 구축 용어로 |
| 각 슬라이드 하단 "한 줄 결론" 바 | 유지 (설계 슬라이드에도 "그래서 이 결정" 한 줄) |
| Research Question 3개 카드 | → Design Question 3개 (무엇을 막을지 / 어디서 막을지 / 누가 승인할지) |
| 표 + 강조 카드 조합 | 유지, 단 숫자 대신 **검사 항목·도구·차단 기준** 표로 |
| 파이프라인 화살표 흐름도 (Raw → Labeling → …) | 그대로 재활용: PR → Build → Test → Lint → Security → Gate → Merge |
| "보안·규제·운영 관점" 슬라이드 | → "게이트 정책·운영 규칙" 슬라이드 |
| 결과 표(AUC/F1) | → **시나리오 검증 계획표** (아직 결과가 없으므로 "이렇게 검증하겠다") |

핵심 전환: **결과가 없어도 설득력 있게** 만들려면, (1) 문제를 실제 코드 예시로 보여주고, (2) 파이프라인을 그림 한 장으로 보여주고, (3) 완성 시 어떤 데모로 증명할지 구체적으로 제시해야 한다.

## 2. 발표 목차 (총 14장, 발표 12~15분)

### 표지 (1장)
- 제목: AI 생성 코드 PR 자동 검증 및 승인 프로세스 구축
- 부제: 2026 2학기 기업모둠학습 주제 제안 | 팀 데굴데굴 | 자문: 클로우플레이크
- 3카드: **Target** 안드로이드 샘플 앱 / **Pipeline** 6단계 검증 게이트 / **Message** "속도보다 통제"

### 목차 (1장)
1. 문제 정의 — AI 코드는 왜 위험한가
2. 목표와 범위 — 무엇을 만들고 무엇을 만들지 않는가
3. 시스템 설계 — 6단계 검증 게이트
4. 검증 계획 — 어떻게 완성을 증명할 것인가
5. 일정·역할·자문 요청

### 섹션 1. 문제 정의 (3장)
- **1-1 현장 문제**: 바이브 코딩의 확산 → "코드는 빨라졌지만 검증은 그대로". AI 코드가 숨기는 4가지 문제(시크릿, 권한, 성능, 이해 부족)
- **1-2 실제 코드 예시**: AI가 실제로 생성하는 위험 코드 3개를 좌우 비교(❌ AI 생성 / ✅ 기대 형태). 예: 하드코딩 API 키, 빈 catch 블록, 모든 인증서 신뢰 TrustManager
- **1-3 Design Question**: DQ1 무엇을 막을 것인가(검사 항목) / DQ2 어디서 막을 것인가(PR 게이트) / DQ3 누가 최종 승인하는가(사람) → 하단 한 줄: "AI 코드도 게이트를 통과해야 병합된다"

### 섹션 2. 목표와 범위 (2장)
- **2-1 목표와 성공 지표**: 취약 PR 10건 차단·정상 PR 5건 통과·10분 이내·커버리지 60%·문서 완비 (표)
- **2-2 범위 정의 (In / Out)**: In: 샘플 앱, CI, 정적분석, 보안검사, 게이트, 문서 / Out: 상용 앱 기능, 자체 분석엔진, AI가 승인 대체

### 섹션 3. 시스템 설계 (4장)
- **3-1 전체 아키텍처**: PR → ① Build → ② Test → ③ Lint → ④ Security → ⑤ AI Review → ⑥ Gate → 승인 → Merge 흐름도 (1학기 파이프라인 슬라이드 스타일 재활용)
- **3-2 검사 항목 × 도구 × 차단 기준 표**: 단계 / 도구 / 검사 내용 / 차단·경고 / 임계값 (Detekt, ktlint, Lint, gitleaks, Semgrep, Dependency-Check, Kover)
- **3-3 AI 생성 코드 특화 검사 8가지**: 일반 CI와 차별되는 항목 (시크릿, 권한, 평문통신, 메인스레드 I/O, 예외삼킴, 복잡도, 테스트 누락, 작성자 이해도)
- **3-4 승인 프로세스와 PR 템플릿**: 브랜치 보호 규칙(필수 체크 + 승인 1인 + 대화 해결) / PR 템플릿의 "AI 생성 여부·자기 설명" 항목 / 게이트 요약 코멘트 목업

### 섹션 4. 검증 계획 (1장)
- **4-1 시나리오 검증표**: 취약 시나리오 10건(번호, 주입 내용, 기대 검출 도구, 기대 결과=차단) + 정상 5건 → "완성 시 이 표가 전부 ✅로 채워지면 성공"

### 섹션 5. 일정·역할·자문 요청 (2장)
- **5-1 6주 로드맵 + 역할**: Phase 1(9/18~9/30 기반) / Phase 2(10/1~10/16 보안·게이트) / Phase 3(10/17~10/30 검증·문서) 간트 + 5인 역할표
- **5-2 자문 요청 사항 5가지**: 필수/경고 기준, 도구 조합, 임계값, AI 리뷰 도입 경험, 우선순위 조정 → 하단: "오늘 자문 결과로 정책을 확정하고 다음 주부터 구현 시작"

### 마무리 (1장)
- 한 줄 요약: "AI로 짠 코드가 자동으로 검증되고, 사람이 이해한 코드만 병합되는 파이프라인"
- 기대 효과: 팀원 전원이 현업 수준 코드 품질 관리 프로세스를 직접 구축·운영한 경험 / 다른 프로젝트에 복사해 쓸 수 있는 템플릿 저장소
- Q&A

## 4. PPT 생성 프롬프트

아래 프롬프트는 Claude, ChatGPT, Gamma, Genspark 등 슬라이드 생성 도구에 그대로 붙여 넣어 사용한다. `[ ]` 안은 필요 시 수정.

### 4.1 전체 덱 생성 프롬프트 (복사용)

```
당신은 소프트웨어 공학 프로젝트 제안 발표 자료를 만드는 전문 디자이너이자 테크니컬 라이터입니다.
아래 조건으로 14장짜리 한국어 PPT를 만들어 주세요.

[발표 개요]
- 제목: AI 생성 코드 PR 자동 검증 및 승인 프로세스 구축
- 성격: 2026년 2학기 SW중심대학사업 기업 모둠학습 "주제 제안" 발표 (아직 개발 산출물 없음, 기획·설계 단계)
- 청중: 산업체 기술이사(클로우플레이크), 지도교수, 팀원
- 발표 시간: 12~15분
- 팀: 데굴데굴 (팀장 박재영, 팀원 최현식·이종서·최미령·장진웅), 지도교수 이석훈, 자문 권진용 기술이사

[디자인 규칙]
- 1학기 발표 자료 스타일 계승: 어두운 남색 배경 표지 + 흰 본문, 각 슬라이드 우상단에 페이지 번호, 슬라이드 하단에 "한 줄 결론" 강조 바
- 표지에 3개 요약 카드: Target(안드로이드 샘플 앱) / Pipeline(6단계 검증 게이트) / Message("속도보다 통제")
- 강조색 1개(파란 계열) + 위험 표시용 빨강, 통과 표시용 초록
- 텍스트는 슬라이드당 최대 6줄, 나머지는 표·다이어그램·카드로 시각화
- 코드 예시는 고정폭 폰트 코드 블록으로, 좌(❌ AI 생성) / 우(✅ 기대 형태) 비교 레이아웃
- 모든 슬라이드에 발표자 노트(30~60초 분량 멘트) 포함

[슬라이드 구성 — 이 순서와 내용을 그대로 반영]
1. 표지 (제목, 부제, 3카드)
2. 목차 (5개 섹션: 문제 정의 / 목표와 범위 / 시스템 설계 / 검증 계획 / 일정·역할·자문 요청, 각 한 줄 부제)
3. 문제 정의 1 — 현장 문제: 바이브 코딩 확산, "코드는 빨라졌지만 검증은 그대로", AI 코드가 숨기는 4가지(하드코딩 시크릿, 과도한 권한, 성능·안정성, 작성자 이해 부족). 하단 결론: "AI 시대 핵심 역량은 생성이 아니라 검증과 통제"
4. 문제 정의 2 — 실제 코드 예시 3개 비교: (a) val API_KEY = "sk-live-..." vs BuildConfig/Secrets 사용, (b) catch (e: Exception) {} vs 로깅·복구·전파, (c) 모든 인증서를 신뢰하는 X509TrustManager vs 기본 검증 유지. 하단: "동작은 하지만 배포하면 안 되는 코드"
5. 문제 정의 3 — Design Question 3카드: DQ1 무엇을 막을 것인가(검사 항목) / DQ2 어디서 막을 것인가(PR 게이트) / DQ3 누가 최종 승인하는가(사람). 하단: "AI 코드도 게이트를 통과해야 병합된다"
6. 목표와 성공 지표 표: 취약 PR 10건 중 10건 차단 / 정상 PR 5건 오탐 0 / 파이프라인 10분 이내 / 핵심 로직 커버리지 60% 이상 / README·정책 문서·온보딩 가이드 완비 / 팀원 전원 PR 플로우 직접 수행
7. 범위 In/Out 2열: In(샘플 앱, GitHub Actions CI, 정적분석, 보안검사, AI 리뷰 봇, 품질 게이트, 브랜치 보호, 문서) / Out(상용 앱 기능, 타 플랫폼, 자체 분석 엔진, AI의 승인 대체). 하단: "앱은 그릇, 게이트가 산출물"
8. 시스템 아키텍처 흐름도: [개발자 AI 코드 생성 → feature push → PR 생성] → ① Build(assembleDebug) → ② Test(단위 테스트+커버리지) → ③ Static Lint(ktlint/Detekt/Android Lint) → ④ Security(gitleaks/Semgrep/의존성 취약점) → ⑤ AI Review(LLM 코멘트, 경고만) → ⑥ Quality Gate(집계·요약 코멘트·상태 체크) → [브랜치 보호: 필수 체크 + 리뷰어 승인] → Squash Merge. 하단: "한 단계라도 실패하면 병합 버튼이 사라진다"
9. 검사 항목 × 도구 × 기준 표 (열: 단계 / 도구 / 검사 내용 / 차단·경고 / 임계값): Build-Gradle-컴파일-차단 / Test-JUnit+Kover-테스트 실패·커버리지-차단-60% / Style-ktlint-스타일-차단 / Quality-Detekt-LongMethod 60줄·ComplexMethod 15·EmptyCatchBlock-차단 / Android-Lint-Error 등급-차단 / Secret-gitleaks-키·토큰-차단 / SAST-Semgrep-HIGH 이상-차단 / Dependency-OWASP·Trivy-CRITICAL 차단·HIGH 경고 / AI Review-Claude API-위험 패턴 설명-경고. 하단: "임계값은 오늘 자문으로 확정"
10. AI 생성 코드 특화 검사 8가지 아이콘 그리드: 하드코딩 시크릿 / 과도한 권한 / 평문 통신·인증서 우회 / 메인 스레드 I/O / 예외 삼킴 / 복잡도 폭증 / 테스트 없는 변경 / 작성자 이해도 미확인. 하단: "일반 CI와 다른 점: 'AI가 짰기 때문에' 보는 항목"
11. 승인 프로세스: 좌측 브랜치 보호 규칙 목록(main 직접 push 금지, quality-gate 필수 체크, 리뷰어 1인 승인, 최신 커밋 기준 승인, 대화 해결), 우측 PR 템플릿 목업(변경 요약, AI 생성 여부·도구, 내 말로 설명한 코드 동작, 테스트 방법, 셀프 체크리스트) + 게이트 요약 코멘트 목업(항목별 ✅❌). 하단: "기계가 거르고, 사람이 이해한 코드만 병합"

```
