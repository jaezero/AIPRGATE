## 1. 명세 해석과 시스템 경계

**M**은 이번 완료에 필요한 필수 요구사항이다. **S**는 필수 기능 완료 후 도입할 선택 사항으로, 구현하지 않아도 M의 인수 조건에 영향을 주지 않는다. 후속 기능은 별도 범위 변경 전까지 구현 약속이 아니다.

조건부 룰 선정은 M을 선택 기능으로 낮추는 뜻이 아니다. 품질·시크릿 검사 범주의 룰을 파일럿으로 확정하고 연결하는 과정까지 필수다. 미확정 룰을 검증한 것으로 표시하거나 후보 도구를 실행했다는 이유만으로 완료 처리하지 않는다.

| 시스템 내부 | 외부 및 제외 |
|---|---|
| 로컬 할 일 앱, 테스트, 검사 설정, 단일 PR workflow, 집계 코드, 협업·보호 정책, 증거 문서 | GitHub 서비스, 개발자가 사용하는 생성 AI, Android SDK·도구 배포처 |
| 신뢰된 팀원의 동일 저장소 브랜치 PR | 외부 fork 자동 실행, 배포·서버·네트워크 기능, AI 리뷰 봇 |

`정책 위반`은 정상 완료된 검사에서 BLOCK 항목을 찾은 상태다. `검사 오류`는 실행 실패·누락·파싱 오류 등 판정에 필요한 근거를 확보하지 못한 상태다. 둘 다 병합을 막지만 원인은 구분한다. `승인 대기`는 자동 검사 결과와 별개다.

| APP-08 | M | ViewModel이 `TaskRepository` 인터페이스에 의존하고 fake 구현을 주입할 수 있어야 한다. | JVM에서 정상·실패 상태 검사 가능 |
| APP-09 | M | 개인정보·실키 없이 테스트 데이터를 사용하고 네트워크·민감 권한을 요청하지 않는다. | Manifest·데이터·로그 리뷰 |

데이터 계약: `Task(id: Long, title: String, isCompleted: Boolean)`. ID는 로컬 DB에서 생성하고 새 항목은 미완료로 저장한다. 제목 중복은 허용하며 화면은 ID 오름차순으로 표시한다. 정렬·중복 정책은 화면과 테스트의 기대 결과를 일치시키기 위한 제품 선택이다. 제목 길이 제한 같은 추가 수치는 필요성을 확인한 뒤 변경 기록으로 도입한다.

화면은 목록과 입력 영역을 중심으로 구성한다. 편집·검색·로그인·네트워크·동기화는 필수가 아니다. Room은 앱 내부 저장소에 둔다. 백업 정책·노출 컴포넌트·로그는 출시 보안 보장 대신 현재 샘플 범위의 수동 검토 결과를 남긴다.

### 2.3 앱 검증

| ID | 등급 | 요구사항 |
|---|---|---|
| TST-01 | M | 목록·빈 상태·정상/공백 추가·대상 토글/삭제·실패·재시도·중복 요청에 assertion이 있는 JVM 테스트를 작성한다. fake repository로 실패를 제어한다. |
| TST-02 | M | Room DAO의 삽입·조회·변경·삭제를 실제 Room 환경에서 검사한다. instrumented test를 기본 방식으로 하며 DB 보존은 에뮬레이터에서 종료·재실행으로 별도 확인한다. |
| TST-03 | M | JVM 테스트는 모든 지원 PR에서 필수 실행한다. 에뮬레이터/Room 검증은 기준 앱 확정 시, DB·DAO·저장 구현 변경 시, 최종 인수 시 수행해 PR 또는 결과표에 연결한다. CI 매회 에뮬레이터 실행은 필수가 아니다. |
| TST-04 | M | 핵심 로직 라인 커버리지를 호환 도구 하나로 측정한다. 패키지·제외 코드·분모·버전을 명시하고 초기에는 보고만 한다. 60% 차단은 사용하지 않는다. |
| TST-05 | M | assertion의 의미와 핵심 경로 누락을 사람이 검토한다. 커버리지 수치나 테스트 파일 변경 여부만으로 테스트 충분성을 판정하지 않는다. |

커버리지 보고는 기준 커밋·최종 인수 및 핵심 로직 변경 검토 시 수행하고, PR별 필수 CI job으로는 초기 등록하지 않는다. 도구 도입 후 실행 명령을 문서화한다. 측정 불가 시 M 미충족으로 남기고 임의 수치를 적지 않는다.

Room 통합 검증은 실제 Android 환경의 DAO 테스트를 기준으로 한다. 메모리 DB의 CRUD 테스트와 앱 종료 후 디스크 데이터 보존은 다른 검증이다. [Room 테스트 공식 안내](https://developer.android.com/training/data-storage/room/testing-db)

## 4. 검사 정책 선정과 실행

### 4.1 정책 요구사항

| ID | 등급 | 요구사항 |
|---|---|---|
| POL-01 | M | PRD 위험 후보 전체를 검토하고 자동·수동·후속·비적용 사유를 기록한다. 위험의 AI 특화 여부를 단정하지 않는다. |
| POL-02 | M | 품질·시크릿 범주별 후보 도구의 버전·배포판·라이선스·룰 ID·입력·출력·종료 코드·비용을 같은 프로젝트에서 확인한다. |
| POL-03 | M | 활성화할 각 룰에 위험 입력·유사 정상 입력을 배정하고, 해당하는 경계·변형과 미탐 한계를 기록한다. 튜닝용과 최종 확인용 입력을 구분한다. |
| POL-04 | M | 품질·시크릿 각 범주에서 검증된 BLOCK 정책을 필수 검사로 활성화한다. 각 정책은 정상 반례와 실제 차단 근거가 있어야 한다. 룰 선정 실패는 범위 재검토 사유이며 완료가 아니다. |
| POL-05 | M | 도구 원본 등급과 프로젝트의 BLOCK/WARN/REPORT를 별도로 저장한다. 미등록 룰은 REPORT로 표시하고 자동 차단 대상으로 확대하지 않는다. |
| POL-06 | M | 예외는 정책 ID·대상·사유·검토자·만료 또는 재검토 조건으로 관리한다. 전체 디렉터리 제외로 위반을 숨기지 않는다. |
| POL-07 | M | 기준·룰·검사 대상·제외·예외 변경을 PR로 검토하고 관련 fixture·FR·검증표를 함께 수정한다. |

Android Lint와 gitleaks는 우선 후보이다. 파일럿 후 대체 시 같은 범주의 근거·반례·출력 계약을 유지하고 결정 기록을 남긴다. Detekt·ktlint·Semgrep·의존성 스캐너를 모두 추가할 의무는 없다.

### 4.2 검사 대상과 한계

- 기본 앱 variant는 `debug`다. debug의 `debuggable`을 출시용 속성처럼 일괄 차단하지 않는다. release 안전성을 검증했다고 표현하지 않는다.
- 품질 검사는 선택한 variant의 앱 코드·리소스에 적용한다. 신규 앱이므로 초기 전체 검사로 시작하고 기존 이슈 일괄 baseline 면제는 사용하지 않는다.
- 시크릿 검사는 검사 커밋의 추적된 소스·설정 파일을 대상으로 시작한다. 과거 전체 Git 이력에서 삭제된 비밀정보까지 검사했다고 주장하지 않는다.
- 시크릿 fixture는 유효하지 않은 테스트 값만 사용한다. 위험 fixture 디렉터리는 제품 스캔과 분리하고 그 제외 이유·범위를 고정한다. 해당 fixture 자체는 별도 룰 검증에서 반드시 검사한다.
- BuildConfig에 넣어 APK에 포함한 서버 비밀키를 안전한 해결책으로 취급하지 않는다. 이번 앱은 외부 API 비밀키를 필요로 하지 않는다.
- 테스트 파일 변경이 없다는 사실, 코루틴의 존재, 높은 커버리지 같은 간접 지표만으로 오류·보안을 판정하지 않는다.

## 5. workflow와 결과 전달 계약

### 5.1 실행 요구사항

| ID | 등급 | 요구사항 |
|---|---|---|
| CI-01 | M | main 대상 `pull_request`의 opened, synchronize, reopened, edited, ready_for_review에서 실행한다. 필수 workflow 전체가 path filter로 생략되지 않도록 한다. draft에서도 검사 가능하며 병합은 GitHub 상태에 따른다. |
| CI-02 | M | `.github/workflows/pr-check.yml` 하나에 `pr-info`, `app-check`, `quality-check`, `secret-check`, `quality-gate` job을 둔다. 앞의 네 job은 독립적이다. |
| CI-03 | M | `app-check`에서 debug 빌드 후 JVM 테스트를 실행한다. 빌드 실패로 테스트를 실행하지 못하면 build failed·test skipped를 구분하고 필수 완료로 처리하지 않는다. |
| CI-04 | M | 집계 job은 모든 필수 job에 의존하며 선행 실패에도 실행을 시도한다. 누락·오류·취소를 성공으로 대체하지 않는다. 전체 workflow 취소 시 게이트 미완료·비성공 상태를 유지한다. |
| CI-05 | M | 동일 PR 실행은 concurrency로 이전 실행을 취소하고, 최신 실행의 식별 정보를 대조한다. 새 커밋과 본문 수정 모두 재평가한다. |
| CI-06 | M | PR head SHA와 실제 checkout SHA를 함께 기록한다. 초기에는 GitHub가 해당 이벤트에 제공한 테스트용 merge SHA를 검사하고 base SHA도 기록한다. checkout 후 실제 SHA를 확인한다. |
| CI-07 | M | 원본 결과·정규화 결과·도구/환경 정보를 같은 run의 고유 artifact로 전달한다. 다른 run의 성공 결과를 재사용하지 않는다. |
| CI-08 | M | Gate 결과와 근거를 Actions job summary 및 artifact로 제공한다. 쓰기 권한이 필요한 자동 PR 코멘트는 필수가 아니다. |
| CI-09 | S | Gradle 등 캐시를 사용한다. 캐시 유무·키를 기록하고 캐시 실패가 검사를 생략시키지 않게 한다. |

집계 스크립트는 단순히 마지막 job 종료 코드만 보지 않고 모든 필수 결과를 검사한다. 병렬 job의 각 실행 환경은 독립적이며 도구 설정·checkout SHA를 일치시킨다. CI 플랫폼이 job을 시작하지 못한 경우도 정상 통과가 아니다. merge conflict로 PR 검사를 실행할 수 없으면 충돌 해결 후 재검사한다. 이벤트·검사 SHA 선택은 [GitHub PR 이벤트 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)를 기준으로 구현한다.

### 5.2 데이터 계약

각 검사 adapter는 원본 출력과 다음 정규화 JSON을 생성한다. 아래는 필드 구조 설명이며 실제 성공 사례가 아니다.

```json
{
  "schema_version": 1,
  "repository": "owner/repository",
  "pr_number": 1,
  "head_sha": "<PR head SHA>",
  "base_sha": "<base SHA>",
  "tested_sha": "<실제 merge checkout SHA>",
  "run_id": "<run ID>",
  "run_attempt": 1,
  "check_id": "quality-check",
  "policy_revision": "<정책 파일 해시>",
  "tool": {"name": "<도구>", "version": "<버전>", "rule_revision": "<룰 해시>"},
  "execution_status": "completed",
  "started_at": "<ISO 8601>",
  "finished_at": "<ISO 8601>",
  "findings": [],
  "error": null,
  "raw_report": "<동일 run artifact 경로>"
}
```

`execution_status`는 `completed | error | cancelled | skipped` 중 하나다. timeout은 `error.code=TIMEOUT`으로 저장한다. 정상 완료와 발견 사항 유무는 별개이므로 도구의 ‘위반 발견’ 종료 코드를 실행 장애로 일괄 변환하지 않는다. 반대로 파싱할 수 없는 출력은 빈 findings로 바꾸지 않는다.

finding 필드: `policy_id`, `rule_id`, `file`, `line`(위치 없으면 null), `tool_severity`, `policy_action`, `message`, `evidence_ref`. 시크릿 원문은 포함하지 않는다. 앱 build/test는 하위 검사별 수행 상태와 실패 건수를 기록한다. `pr-info`에는 사용한 본문의 해시·PR 갱신 시각을 추가한다.

artifact 이름은 check ID·run ID·attempt를 포함해 구분한다. 집계는 스키마, 필수 check ID의 누락·중복, 실행 식별값, 정책 revision, 원본 위치를 확인한다. 리포트 내용은 데이터로 파싱하며 실행 파일이나 shell 명령으로 사용하지 않는다.

### 5.3 최신 결과와 정책 변경

집계 직전에 PR의 현재 head/base 및 본문 정보를 다시 읽어 해당 실행 입력과 대조한다. 달라졌거나 조회에 실패하면 통과시키지 않고 갱신·재실행 필요로 표시한다. 본문 수정으로 같은 SHA에 여러 실행이 생겨도 최신 본문 해시와 맞지 않는 결과는 성공으로 게시하지 않는다. concurrency와 이 대조를 함께 사용한다.

기준 브랜치가 변경되면 최신 상태 요구 설정에 따라 브랜치를 갱신하고 재검사한다. PR 본문 변경 자체를 GitHub가 코드 변경처럼 항상 승인 무효화한다고 가정하지 않는다. 리뷰어는 병합 직전 최신 본문·AI 기록을 확인하는 운영 책임을 가진다.

workflow·gate·정책·adapter를 PR 작성자가 변경하면 판정 체계 자체가 바뀔 수 있다. 해당 변경에는 담당자의 별도 검토와 회귀 검증 기록을 필수로 요구한다. 이 MVP는 PR 작성자의 악의적 리포트 위조를 자동 방지하는 보안 경계라고 주장하지 않는다.

필수 체크 이름은 다른 workflow와 중복되지 않는 `quality-gate`로 통일한다. 버튼의 모양 대신 실제 병합 제한과 거부 사유를 검증한다. skipped·neutral을 안전한 실패로 가정하지 않는다. [GitHub 필수 체크 처리](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

| 입력 상태 | 집계 판정 | 병합 조건 |
|---|---|---|
| 필수 완료, BLOCK 없음 | PASS | 별도 승인·최신성 조건 충족 시 가능 |
| 필수 완료, BLOCK 있음 | POLICY_FAIL | 차단 |
| 필수 실행 오류·누락·파싱 실패·skipped | CHECK_ERROR | 차단 |
| WARN/REPORT만 존재 | PASS + 경고 | 별도 승인 필요 |
| 오래된 head/base/본문 또는 실행 불일치 | STALE 또는 CHECK_ERROR | 재검사 전 차단 |
| workflow 전체 취소·집계 미실행 | 성공 없음 | 차단 상태 확인 |
| 자동 PASS, 사람 승인 없음/변경 요청 | 자동 PASS 유지 | 보호 규칙에서 보류 |

GitHub check conclusion은 위 내부 판정을 success/failure 등으로 매핑하고 상세 원인은 summary에 남긴다. ‘검사를 못 했지만 위험을 찾지 못했으므로 통과’하는 경로는 없다.

## 8. 검증 설계·인수 기준·추적

### 8.1 사례 수 도출

1. M 요구사항과 선정 정책을 검증표에 등록한다.
2. 앱은 정상·실패 동작, 룰은 위험·유사 정상·필요한 경계/변형, 집계는 상태 분기를 배정한다.
3. 같은 경로의 반복은 로컬 fixture로 검사하고 실제 PR에는 연결을 확인할 대표 사례를 배정한다.
4. 최종 평가 입력을 튜닝 입력과 분리한다. 분리하지 못한 경우 회귀 검증으로 한정해 보고한다.
5. 실행 전에 예상 결과와 근거를 작성하고 목록을 고정한다. 실제 결과·실패·재검증을 별도로 기록한다.

아래 AC 행 수는 PR 수가 아니다. 하나의 PR에서 여러 SHA·상태를 확인할 수 있으나 각 상태의 증거를 분리한다. unrelated 위반을 한 커밋에 몰아 넣어 검출 원인을 모호하게 만들지 않는다.

| AC-12 | NFR-01~03, PR-06 | 최소 권한·키 미전달·입력 처리·fork 제외·정책 변경 리뷰 책임 확인 | 설정 리뷰·입력 fixture |
| AC-13 | NFR-04~09 | 반복 결과·시간·비용 조건·실패 안내·증거 보존·다른 팀원 재실행 확보 | 운영·측정 기록 |

검사용 실패·취소·위반 PR은 main에 병합하지 않는다. 보호 동작 시험은 삭제·복구가 쉬운 테스트 변경을 사용하며, 실제 자격증명을 유출시켜 탐지 여부를 시험하지 않는다.

### 8.3 결과표 형식과 지표

`case_id / 연결 FR·AC·policy_id / 계층 / 생성·주입 유형 / 입력·기대 결과·정답 근거 / 튜닝·최종 구분 / 실제 결과 / 도구·룰 / PR·head·tested SHA / run·attempt / 로그·캡처 / 실행 시각·소요 시간 / 장애 원인 / 검토자 / 재검증 연결`을 기록한다.

- 정책 일치: 기대한 집계 판정과 일치한 사례 / 전체 정책 사례.
- 목표 위험 검출: 목표 룰이 목표 문제를 검출한 사례 / 위험 사례.
- 정상 오탐: 정상 사례에 부당한 finding이 나온 사례 / 정상 사례.
- 정상 병합 차단: 정상 사례가 차단된 건수와 코드·설정·실행 장애 원인.
- 실행 장애: timeout·취소·다운로드 실패·누락 등을 별도 집계.

분모 0은 해당 없음으로 표시한다. 표본이 작으면 건수·실패 사례를 중심으로 보고하며 일반 정확도 100%·오탐 가능성 0으로 표현하지 않는다. 무관한 빌드 실패로 막힌 PR을 시크릿 검출 성공으로 세지 않는다.

## 9. 저장소 구조와 실행 가이드 계약

아래는 개발할 저장소 구조이며 현재 파일이 이미 존재한다는 뜻이 아니다.

```text
ai-pr-gate-android/
  app/src/main/                    # UI, ViewModel, Repository, Room
  app/src/test/                    # fake 기반 JVM 테스트
  app/src/androidTest/             # 실제 Room 통합 테스트
  gradle/                          # Wrapper·버전 정의
  gradlew / gradlew.bat
  .github/workflows/pr-check.yml
  .github/PULL_REQUEST_TEMPLATE.md
  tools/gate/                     # adapter·schema·집계 및 상태 테스트
  config/                         # 채택 룰·정책·예외
  verification/fixtures/          # 비활성 룰 검증 입력, 제품 스캔 제외 범위 명시
  docs/environment.md
  docs/risk-selection.md
  docs/policy-decisions.md
  docs/architecture.md
  docs/verification-matrix.md
  docs/results/
  docs/ai-evidence/               # 공개 가능한 생성 기록 또는 접근 통제된 원본 참조
  README.md
```

앱 모듈 `app`·variant `debug` 기준 초기 명령:

```powershell
# Windows: Android Studio Terminal, 프로젝트 루트
.\gradlew.bat :app:assembleDebug
.\gradlew.bat :app:testDebugUnitTest
.\gradlew.bat :app:lintDebug
# 에뮬레이터 연결 후 Room 통합 검사
.\gradlew.bat :app:connectedDebugAndroidTest
```

CI에서는 같은 task를 `./gradlew`로 실행한다. 실제 프로젝트 생성 후 `tasks` 출력으로 이름을 확인하고 README와 workflow를 맞춘다. 시크릿·커버리지·집계 명령은 도구 파일럿 완료 시 버전·설정·실행 디렉터리·기대 종료 코드와 함께 확정한다. 문서에 없는 로컬 수작업에 CI가 의존하지 않게 한다.

## 10. 개발 단계와 변경 관리

| 단계 | 우선 구현 요구사항 | 종료 조건 |
|---|---|---|
| A 환경 | ENV 전체, POL-01, EVD-01 | 환경·범위·보호 기능·담당 확정 |
| B 앱 | APP 전체, TST-01~03, EVD 전체 병행 | 기준 앱·핵심 테스트·원본 기록 |
| C 첫 PR 연결 | PR-01~02, CI 골격, GAT 기본, GOV | 빌드·테스트의 통과/실패 및 승인 연결 |
| D 파일럿 | POL 전체, TST-04~05, NFR 측정 | 품질·시크릿 정책과 반례 확정 |
| E 강화 | PR-03~05, CI·GAT·GOV 전체, NFR-01~03 | 누락·취소·최신성 등 필수 경로 구현 |
| F 인수 | AC 전체, NFR-04~09 | 실제 결과·잔여 한계·교차 실행 |

정확한 일정과 담당은 가용 시간 확인 후 배정한다. 필수 범위를 줄여야 한다면 PRD 목표·FR·AC·발표 약속을 함께 개정한다. 미확정 도구 버전·룰·계정 기능을 추정해서 성공으로 채우지 않는다.

### 기존 명세에서 폐기한 약속

- 모든 앱에 Room·Retrofit을 함께 요구하던 조건.
- 15개 독립 PR, 커버리지 60%, 실행 시간 10분의 사전 고정.
- 60줄·복잡도 15 일괄 차단과 근거 없는 메인 스레드 커스텀 룰.
- AI 리뷰 봇·의존성 스캔·TLS 우회 탐지를 필수 성과로 다루던 조건.
- Manifest 속성 일괄 차단, 모든 시크릿 검출 보장, 승인으로 이해도 보장.
- PR 코멘트 자동 게시·SARIF 업로드·Squash 방식 자체를 핵심 완료 조건으로 삼는 것.

공식 기술 문서는 2026-09-20 확인 기준이며 실제 구현 시 선택한 환경에서 검증한다. 이 문서가 요구하는 증거는 앞으로 확보할 산출물이다.
